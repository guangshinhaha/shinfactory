# Per-Order Spending Cap Gates The Launch, Not The Run

- `loop/order_spend.go`: `.noodle/order-spend.json` keys by order ID (a retry is a fresh order with the same ID, like `failed-rounds.json`). Both files are written atomically (`filex.WriteFileAtomic`). Launches count per stage task key at dispatch; cost sums `session.TotalCost()` in `trackCookCompleted`, which every stage end passes through (done, killed, cancelled, steered, shutdown-leaked).
- Attempts count within a fix round (`orderSpend.Round`; a lower round never resets it, and a cost for an order with no launch on record is dropped). A quality reject reopens the order at `Round+1` (capped by `maxFixRounds`), which resets the attempts and keeps the cost, so reject loops do not eat the failure-retry cap.
- `spawnCook` checks `[spend]` (`max_attempts` 3, `max_cost_usd` 20) before creating the worktree. Over a cap: `stopOverCap` fails the order, then `stopForPerson` comments once and swaps `ready` for `needs-shin` (see [[codebase/needs-shin-stop-path]]). The ledger clears on stop, on the order's `done`, and on `controlSkip`.
- Limits: cost is only known when a stage ends, so one stage can pass the ceiling before the order stops. Adopted sessions report cost 0, and a stage lost to a restart never reports. A failed order that is never stopped, skipped or finished keeps its entry, because its retry reuses the count.
- Caps of zero or less are off in the loop; `config` normalizes them to the defaults.
